# 已知限制

> 從 README 搬過來的詳細說明。快速開始見 [README](../README.md)。

依主題分成 5 組。「之後可以怎麼做」是初步想法，**尚未實作**，之後的版本再逐項評估。

## 1. 官方行情與更新

| 限制 | 為什麼 | 目前怎麼處理 | 之後可以怎麼做 |
|---|---|---|---|
| **持股超過約 500 檔（不同代號）時，無法保證公布後一小時內全部更新** | 題目指定的 API 一次只能查「一檔、一個月」，每次間隔 6 秒避免被阻擋：10 分鐘＋檔數 × 6 秒 ≤ 60 分鐘 → 約 500 檔（月初約 250 檔） | 同一代號只查一次；已拿到當天收盤價、13:30 前、休市日都不查；數十檔一輪只要幾分鐘 | 改用證交所 `STOCK_DAY_ALL`、櫃買中心 OpenAPI「一次查全部」（網址要跟著 `TWSE_BASE_URL`／`TPEX_BASE_URL` 一起換），查不到再退回題目的 API |
| 伺服器剛啟動時，部分股票先顯示「更新中…」 | 第一輪要逐檔查詢（每次間隔 6 秒） | 啟動後立刻開始查；有上次收盤價時一併顯示 | 改用「一次查全部」後，第一輪幾秒內完成 |
| 颱風假等臨時休市 | 不在官方休市日清單中 | 16:00 後同一檔連續 3 次查不到當天收盤價，當天就不再查；顯示最近一個交易日的收盤價 | 串接官方的臨時休市公告 |
| 休市日資料只有 2021～2027 年 | 官方只提供這幾年（2020 年以前回應成功但內容是空的，2026-11-21 實測） | 有網路時自動向官方取得新年份；空的資料當成「沒有資料」；2.0 網頁沒有資料的年份只檢查週末 | 每年把新年度放進 `src/main/resources/holidays/`；或把休市日存進資料庫 |
| 多台伺服器時，每台各自查詢 | 快取與排程放在記憶體 | 單台部署 | 共用快取（例如 Redis），只讓一台執行排程 |

## 2. 股票的上市、下市與種類

| 限制 | 為什麼 | 目前怎麼處理 | 之後可以怎麼做 |
|---|---|---|---|
| **只支援已上市或已上櫃之股票**（興櫃、未公開發行的股票不能記錄） | 題目指定的行情來源只有證交所、櫃買中心的上市、上櫃成交資料；興櫃沒有收盤價（只有成交均價） | 查不到時回「查無股票代號…（只支援上市、上櫃的股票）」，資料不儲存 | 串接櫃買中心興櫃行情，並另外定義興櫃的盈虧算法 |
| 不檢查交易日期當時這檔是否已上市、是否已下市（例如打錯年份） | 記帳 App 通常不查：記的是使用者自己的真實交易；查證要多打官方 API，官方連不上時還會誤擋正確的資料 | 只擋未來日期與 1990-01-01 以前 | 送出時查那個月有沒有成交，只提醒、不擋 |
| 已下市的股票：App 1.0 與第一版網頁無法新增 | 1.0 沒有交易日期，只能查近兩個月 | 2.0（App 2.0 與 2.0 網頁）補登舊交易時，近兩個月查不到會改查「交易日期那個月」，那個月有成交就可以記錄 | — |
| 2010 年以前已下市的上市股票，無法補登 | 證交所的個股日成交資訊只提供 2010-01-04 起的資料（櫃買中心可查到 2000 年以前） | 回「查無股票代號」，訊息說明證交所只提供 2010 年起的資料 | — |
| 無法明確判斷「已下市」 | 題目指定的 API 只有成交資料，沒有上市狀態 | 近兩個月沒有成交時，往前多查 4 個月找最後收盤價，顯示「近期無成交資料（可能停止交易或已下市）」 | 參考官方證券清單；但考官的測試伺服器沒有這份資料，只能補充說明、不能推翻題目 API 的結果 |
| **無法處理分割事件**：股票分割、減資、合併或股份轉換不會自動調整（例如 0050 於 2025 年 6 月一拆四；2311 日月光換成 3711 日月光投控） | 題目指定的 API 沒有分割、減資資料；在交易上直接改價格會失真（價格只存到小數兩位，例如 180.05 ÷ 4 = 45.0125）。第 7 題評估「分割調整」約需 4.5～5.5 小時，這次先不做 | 請使用者把分割前的交易改成分割後的股數、價格（0050：2 張 180 元 → 8,000 股 45 元，金額與手續費不變，成本完全相同）；合併、股份轉換在新代號記一筆買進。客服回覆範本見 `ISSUES.md` 回報一 | 新增「分割事件」紀錄：原始交易不動，計算到分割日時股數 × 比例、總成本不變（成本精確、可刪除復原） |

> 上市 ↔ 上櫃、興櫃 → 上櫃：依《中華民國證券市場編碼原則》「一碼到底」，**代號不變**；排程會自動更新市場別，兩個市場的手續費、證交稅相同，舊交易的計算不受影響。

## 3. 2.0 記帳規則

| 限制 | 為什麼 | 目前怎麼處理 | 之後可以怎麼做 |
|---|---|---|---|
| 同一天的多筆交易，依輸入的先後順序計算 | 只記日期、沒有成交時間 | 先依日期、同一天再依輸入順序；要調整順序請刪除後重新記錄 | 記錄成交時間 |
| 修改或刪除過去的交易，之後的已實現損益都會重算 | 一律依交易紀錄從頭重算（資料只存一份） | 造成某一天賣超時擋下，並說明是哪一天、當時持有多少 | — |
| 1.0 轉入的持股沒有真正的買進日期 | 1.0 只記錄「新增的時間」 | 用新增那天當買進日期並標記「推估」；補登更早的賣出被擋下時，訊息附上修改那筆買進的連結 | — |
| 伺服器不擋週末、休市日 | 記的是使用者自己的交易，硬擋會誤擋正確的資料 | 2.0 網頁提醒「這天可能不是交易日，確定嗎？」並確認一次；App 2.0 由 App 決定 | — |
| 交易時間線不合理（例如直接改資料庫）時，那一檔算不出來 | 正常操作不會發生（寫入前都會重算並擋下賣超） | 只把那一檔標成「資料異常」並記錄錯誤 log，其他持股照常；交易明細照樣列出讓使用者修正。**沒有主動告警** | 啟動時掃描全部持股、資料檢查 API、接上告警 |

## 4. App 1.0 相容

| 限制 | 為什麼 | 目前怎麼處理 | 之後可以怎麼做 |
|---|---|---|---|
| **App 1.0 看 2.0 的資料不完整**：零股捨去、看不到已實現損益與已全部賣出的股票 | App 1.0 已發布，`lots` 只能是整數、沒有已實現損益欄位 | 金額用真實股數計算；名稱後加註原因，例如「台積電【請更新 App 2.0：含零股 500 股】」 | App 1.0 使用者減少後停止 v1（先加 `Sunset` 標頭預告） |
| **App 1.0 與第一版網頁不能修改、刪除在 2.0 操作過的持股** | 1.0 只有「張數＋買進價」，修改會毀掉 2.0 的買賣紀錄 | 回 409 `UPGRADE_REQUIRED`，訊息請使用者更新到 App 2.0 | — |
| 1.0 的金額只到「元」，可能和 2.0 差幾元 | 規格規定金額是整數 | 每筆先四捨五入再加總；第一版網頁出現這種持股時加註說明 | — |
| 第 2 題時期新增、還沒查到市場別的舊持股，App 暫時看不到 | API 規格規定 `market` 不可為 null | API 暫不輸出（單筆回 404），網頁照常顯示；排程查到市場別後就會出現 | — |

## 5. 使用與部署

| 限制 | 為什麼 | 目前怎麼處理 | 之後可以怎麼做 |
|---|---|---|---|
| 手機與電腦同時寫入同一檔時，後到的要排隊；等超過 3 秒會失敗 | 寫入前先鎖住那一檔（悲觀鎖）才能保證不賣超；等太久 App 會一直重送 | 鎖通常只佔幾毫秒；超過 3 秒回 409「請稍後再試」；同一筆被兩邊修改時用版本號偵測，不會默默覆蓋 | 依使用量調整等鎖上限 |
| 沒有登入與使用者帳號 | 題目與 App 1.0 API 都沒有使用者的概念 | 單一使用者使用 | 加帳號與權限 |
| 2.0 網頁只做電腦版 | App 2.0 由另一個團隊照 API 製作，手機使用者主要用 App | 寬度小於 1100px 時出現水平捲軸 | 手機版網頁 |
| 2.0 網頁沒有「全部交易」頁 | 每一檔的明細已能完成題目要求 | 交易在各檔的明細頁 | 所有交易依日期列在同一頁 |
| 升級 2.0 後無法直接改回 1.x 程式 | 2.0 的 migration（V6）刪除了 1.x 使用的欄位 | 升級前先備份；要回到 1.x 時「還原備份＋舊版程式」 | — |
